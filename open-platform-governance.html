0

现状诊断与设计目标

先把当前链路的四类核心痛点定位清楚，再对应给出体系化解法——本方案的每一节都在回应这些痛点。

当前链路的四大痛点

① 上传前：无自测、标准不透明
用户不知道平台要求什么、自己的资源合不合格，只能在 WorkBuddy 里手动试一下就盲传，没有任何"提交前体检"手段。
→ 解法：标准全公开 + 自助检测工具（Linter + 沙箱试运行）
② 审核中：黑盒、问题定位不清
系统只给"大概的问题"，指不到具体哪行、怎么改，每次都要拉开发和合作方一起看，沟通成本极高。
→ 解法：分级审核 + 结构化问题码（可定位、附修复建议）
③ 无标准：分类/准入无依据
哪些合作方、什么样的资源符合接入标准，没有明文分级，也没有"选 Skill 还是专家还是连接器"的判定规则。
→ 解法：分类选型规则 + 分级准入门槛（P0/P1/P2）
④ 上架后：无后链路、看不到效果
上架即失联，不知道线上表现、稳定性、用户反馈，出问题只能自己去体验才发现，没有监控和退出机制。
→ 解法：质量分 + 运行监控 + 灰度/巡检/下架闭环

体系设计目标（四个"化"）

◱标准化
  • 三类资源各有明文、可核对的准入标准与提交清单
  • 审核规则、评分维度、SLA 全部公开可查
◱透明化
  • 提交前可自测，问题反馈可定位到行、附修复建议
  • 审核进度、状态、后链路数据对合作方可视
◱安全化
  • 凭证/权限/数据/网络四层安全基线贯穿全链路
  • 按风险分级管控，高风险强制人工+安全评审
◱度量化
  • 统一质量分模型，上架后持续打分
  • 低分自动预警、灰度、限流直至下架

先分类：三类资源的定位与选型规则

连接器、Skill、专家不是平行竞品，而是「连接外部 → 封装能力 → 打包角色」的三层递进。分类错了，后面所有标准都会错位。
资源类型一句话定位本质典型场景核心风险面
连接器 Connector让 AI 能接触外部系统的入口数据/操作的通道（MCP / CLI）接公司自有 API、第三方 SaaS、内部系统凭证、鉴权、数据出境、服务稳定性
Skill让 AI 会做某类活儿的说明书流程/方法的封装固定套路反复做（如按模板出文档）提示注入、越权指令、脚本执行
专家 Expert把人设+知识+Skill+连接器打包成的角色完整角色（可含团队编排）需要固定人设+方法论+数据的岗位上述全部 + 内容合规、头像合规
◆
选型判定规则（内置到提交入口的向导）：问题本质是"接不上外部数据/操作" → 选连接器；是"同一套活儿反复做" → 选Skill；是"要一个有人设、有方法论、能调数据的完整角色" → 选专家（专家内部可同时挂载多个 Skill / 连接器）。提交入口第一步就用三个问题把用户导到正确类型，避免错分类。

阶段一 · 引入准入：合作方与资源分级

解决"哪些合作方/资源符合接入标准没标准"的问题——先给合作方分级、给资源定风险级，后续审核力度按级匹配。

合作方分级（决定审核力度与权限）

级别典型对象准入要求权限与待遇
S · 战略合作标杆生态伙伴、深度定制方商务签约 + 安全协议 + 专属对接人绿色通道、联合运营、优先推荐位
A · 认证开发者企业主体、通过资质认证企业实名 + 历史合规记录良好标准 SLA、可提交高风险类资源
B · 普通开发者个人/小团队开发者实名注册 + 同意开发者协议仅可提交低/中风险资源，审核从严

资源风险分级（决定审核路径，见阶段四）

P0 高风险
涉资金/支付、可写外部系统、访问敏感个人数据、需数据出境、可执行本机命令。强制安全评审。
P1 中风险
读写业务数据、需 OAuth/Token 鉴权、有外呼调用。机审+人审。
P2 低风险
纯本地流程 Skill、只读公开数据、无凭证、无外部副作用。机审为主+抽检。

风险级 × 合作方级 = 审核矩阵：如 B 级开发者提交 P0 资源默认不受理，需先升级为 A 级或走 S 级担保。

4

阶段二 · 开发自测：把标准前置，让用户自己测

这是解决"上传前不知道要求、没测试工具"最关键的一段——用「标准公开 + 自助检测工具」把审核标准前移到开发者手里。

① 标准全公开：开发者门户（Developer Hub）

在配置平台建立公开的「开发者门户」，把此前散落的规范集中沉淀为可检索的标准中心：

接入规范（连接器 v3.0 / 专家 v2.3）提交检查清单命名规范 凭证与安全要求性能基线（QPS/延迟/超时）内容合规红线评分维度与权重审核 SLA完整示例模板

② 自助检测工具（提交前必须绿灯）

1结构 Linter
  • 校验文件结构、必填字段、命名规范
  • 一致性约束（如 plugin.json 各 ID 对应关系）
  • 秒级返回，问题定位到字段/行
2安全扫描
  • 检测硬编码 Token/密钥、危险指令
  • 提示注入模式、越权工具声明
  • 凭证占位与 headers 一一对应校验
3沙箱试运行
  • 隔离环境真实加载资源并跑用例
  • 连接器可跑连通性/压测预检
  • 输出运行录像与调用轨迹供自查
▲
连接器专项——性能基线自测（源自 v3.0 规范硬指标）：提交前须用 k6/wrk 完成压测并达标：QPS ≥ 50 P50 ≤ 500ms P99 ≤ 3000ms 超时率 < 1% 错误率 ≤ 0.5% 并发长连 ≥ 200 SLA ≥ 99.9%。工具自动生成压测报告模板，开发者一键校验是否达标。
  • 自测工具与线上审核共用同一套规则引擎——自测绿灯 = 机审必过，杜绝"自测过了审核却挂"的割裂感
  • 自测报告随提交包一起带上，审核员可直接复用，减少重复核对
  • 门户提供三类资源的脚手架模板（一键生成合规骨架），从源头降低出错率

阶段三·四 · 提交与分级审核：把黑盒变透明

解决"审核黑盒、问题指不清、每次都要拉人一起看"——用「三级审核流水线 + 结构化问题码」让反馈可定位、可自助修复。

三级审核流水线

A
机审（自动）
复用自测规则引擎

分钟级出结果
B
人审（内容质量）

路径按风险级自动分流：P2 机审通过即可（抽检人审）；P1 机审→人审；P0 机审→人审→安审，三关全过方可上架。

结构化问题码：让"大概的问题"变成"可定位可修复"

审核系统对每个问题输出统一格式：问题码 + 位置 + 原因 + 修复建议 + 参考文档链接。开发者无需拉人即可自助修复：

# 审核反馈示例（结构化、可定位） ✗ [SEC-013] 硬编码凭证 文件: skills/SKILL.md 行: 42 原因: 检测到明文 API Key「sk-xxxx」，违反凭证安全基线 修复: 改用 ${API_KEY} 占位，并在 tokenSchema.fields 声明；见《连接器规范 v3.0 · 第7章》 ✗ [CONSIST-002] 一致性约束不通过 文件: plugin.json 字段: agentName 原因: agentName「sales-bot」≠ Agent MD 文件名「sales_bot.md」 修复: 三者需一致（agentName = 定义文件 name = 文件名），统一为 sales-bot ⚠ [PERF-005] 性能基线未达标 压测报告 指标: P99=4200ms 原因: P99 延迟超出 3000ms 上限 修复: 优化慢接口或提升服务规格后重新压测
问题码分域
  • STRUCT- 结构/文件/字段　CONSIST- 一致性约束
  • NAMING- 命名规范　SEC- 安全/凭证
  • PERF- 性能基线　CONTENT- 内容合规
  • META- 描述/图标　FUNC- 功能完整性
审核体验保障
  • 状态全程可视：已提交/机审中/待人审/需修改/已通过
  • SLA 公开：机审分钟级、人审 3 个工作日内出结果
  • 一次性返回全部问题，避免反复往返打回
  • 驳回附可复现步骤，开发者本地即可验证

贯穿全链路的安全基线（四层）

解决"不安全"——安全不是审核某一关，而是四层基线在自测、审核、运行全程强制校验。多数条目源自现有 MCP OAuth 与连接器安全规范。
① 凭证安全
  • 严禁硬编码 Token/密钥（机扫强制拦截）
  • OAuth2.0 + PKCE；Token 由平台安全存储与自动刷新
  • 用户自填 Token 走 tokenSchema，占位与 headers 一一对应
② 权限最小化
  • 只申请必要工具与数据范围，专家不得私自声明 tools
  • 可写/高危操作需二次确认与显式授权
  • 权限变更须重新审核
③ 数据安全
  • 敏感数据传输强制 HTTPS（localhost 除外）
  • 数据出境/驻留需声明并合规评估
  • 最小采集、用途透明、不留存无关数据
④ 网络与运行
  • redirect_uri 严格匹配、state 防 CSRF、授权码一次性
  • 服务出站可管控，超时/异常有兜底
  • 沙箱隔离运行，越权访问即阻断
攻击/风险防护机制校验环节
凭证泄露禁硬编码 + 平台安全存储 + 自动刷新自测机扫 / 机审
授权码拦截 / CSRFPKCE + state 校验 + redirect_uri 精确匹配安审（P0/P1）
提示注入 / 越权指令注入模式扫描 + 工具权限白名单安全扫描 / 人审
数据违规出境数据流声明 + 合规评估安审
服务不稳定拖垮体验压测达标 + 上线后可用性监控自测 / 后链路

阶段五·六 · 灰度上架与后链路运营

解决"上架后失联、不知道效果"——用「灰度观察 + 统一质量分 + 运行监控 + 退出机制」把上架从终点变成运营起点。

灰度上架

审核通过后不直接全量，先小流量灰度（限定用户群/比例），设 7~14 天观察期，达标才转全量；灰度期异常可秒级回滚，不影响大盘。

角色权责与落地节奏

体系要跑起来，靠的是清晰的权责分工 + 分期落地，避免一次性铺太大。

全链路 RACI（谁负责什么）

环节合作方/开发者平台运营（贵部门）研发/安全
标准与工具遵循 · 反馈制定 · 维护建工具 · 提供规则引擎
自测执行 · 达标提供门户与模板维护 Linter/沙箱
审核提交 · 修复人审 · 决策机审引擎 · 安审支持
上架/灰度确认灰度策略 · 放量灰度与回滚能力
后链路响应整改监控 · 巡检 · 处置监控看板 · 告警

分三期落地

一期 · 立标准
  • 开发者门户上线，标准全公开
  • 结构 Linter + 安全扫描（复用现有规范）
  • 结构化问题码接入审核反馈
  • 先解决"标准不透明+黑盒"
二期 · 建闭环
  • 沙箱试运行 + 压测预检
  • 三级分级审核流水线
  • 灰度上架 + 质量分模型
  • 补齐"自测+分级+后链路"
三期 · 精运营
  • 后链路监控看板 + 自动预警处置
  • 合作方分级权益 + 联合运营
  • 质量分驱动的推荐与激励
  • 从"管住"到"运营好"
◆
一句话总结体系价值：把"做完盲传→黑盒审核→上架失联"的原始链路，升级为"标准可查、提交前自测绿灯、审核可定位、上架先灰度、线上有分有监控"的透明闭环——用户体验更好、安全底线更稳、生态质量水位更高。
